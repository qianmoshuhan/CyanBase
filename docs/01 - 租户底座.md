## 核心定义：多租户三层拦截器链（TenantMybatisPlusConfig 注册）
**TenantMybatisPlusConfig.java** 注册三层拦截器链（顺序不能反）：
```
外层（先执行）：PaginationInnerInterceptor     → 分页 / 物理删除
中层（后执行）：DataPermissionInterceptor       → 追加 dept_id / create_by 过滤（@DataScope）
内层（最后执行）：TenantLineInnerInterceptor    → 追加 tenant_id 过滤
```

TenantLineInnerInterceptor 必须最后执行，否则分页 SQL 里的租户条件会被分页器当成业务条件。

```java
@Bean(name = "tenantMybatisPlusInterceptor")
@Primary
public MybatisPlusInterceptor tenantMybatisPlusInterceptor(...) {
    MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
    interceptor.addInnerInterceptor(new PaginationInnerInterceptor());          // 外层
    interceptor.addInnerInterceptor(dataPermissionInterceptor);                 // 中层
    interceptor.addInnerInterceptor(new TenantLineInnerInterceptor(handler));   // 内层
    return interceptor;
}
```

> ⚠️ 必须加 @Primary，否则 MyBatis-Plus 自动配置找不到哪个 Bean 要用。

### 后处理逻辑也必须同步（2026-11-06 P0 补充）

> 只抄接口签名还不够——**写操作成功后的副作用逻辑（如清 Redis 缓存、触发权限版本 bump）也必须两边同步**。
>
> **反面教材（2026-11-06 实际发生）**：权限版本预埋改造时，只在平台侧 `SysRoleController` 三个变更点加了 `bumpVersionForRole`，完全漏掉租户侧镜像——租户侧用户改角色名称/dataScope/菜单，**永远不触发 bump**，关联用户版本号不变。

```
❌ 漏改链路：
租户管理员操作角色 → 请求走 /tenant/role/** → 进入 TenantRoleController
→ SysRoleController 里的 bump 调用根本不会被执行！

✅ 正确做法：平台侧每加一处 bump 调用，租户侧镜像必须 grep 同步
```

### 租户侧独有的接口

租户侧除了复刻平台侧全套接口，还存在租户独有接口，示例：`GET /tenant/role/availableMenus` 获取该租户角色可分配菜单，该接口平台侧不存在，租户侧需要单独实现。

## 4. 多租户 SQL 自动注入

TenantLineInnerInterceptor 在所有 INSERT / UPDATE / DELETE / SELECT 的 WHERE 里自动追加：

```sql
WHERE ... AND tenant_id = 当前用户的 tenantId
```

**例外**：SysTenantController（租户管理本身）、超管用户（tenantId=0）、显式排除的表。

## 执行流程：PermissionGuard L1 租户硬隔离主动校验

👉 参考：00-README.md [核心定义-三层执行门槛 vs 三层拦截器链]

> 2026-10-23 落地。原来散放在 TenantRoleController（7处）/ TenantUserController（5处）/ TenantDeptController（2处）里的 `tenantId.equals(exist.getTenantId())` 租户归属比对，已全部统一到 PermissionGuard 的 L1 层。

### L1 校验逻辑（不可拆分，2026-11-07 订正：覆盖平台主体三种分支）

```
doCheck() 入口 → 超管放通（userId=0 或 permissions 含 *:*:*）→ return
    ↓ 非超管
checkTenantIsolation(targetScope)
    ↓
步骤 1.1  登录态：userId != null → 401 "请先登录"
    ↓
步骤 1.2  分支判断（按优先级）：

    ┌─ 分支 A：platformPrincipal=true + activeTenantId!=null
    │   → 跨租户许可校验（principal_tenant_scope 查表）
    │   → 资源租户归属比对（targetScope.targetTenantId == null 跳过）
    │   → ✅ 通过后：📝 写审计日志 CROSS_TENANT_ACCESS（仅 targetScope!=null 写操作）
    │   → 继续 L2 DataScope + L3 RBAC
    │
    ├─ 分支 B：tenantId > 0（普通租户用户 OR 平台主体未选活跃租户但 tenantId>0）
    │   → 资源租户归属比对（targetScope.targetTenantId == null 跳过）
    │   → ✅ 通过后：📝 平台主体（platformPrincipal=true）也写审计日志 CROSS_TENANT_ACCESS（仅 targetScope!=null 写操作）
    │   → 普通租户用户不审计（正常业务行为）
    │   → 继续 L2 DataScope + L3 RBAC
    │
    └─ 分支 C：拒绝
        情况：platformPrincipal=true + activeTenantId=null（未选活跃租户）
             tenantId=0（理论上不会走到，入口已放通）
             tenantId=null + 非平台主体
        → 403 "当前主体无权访问租户接口"
```

> ⚠️ **2026-11-07 关键订正**：platformPrincipal=true **不等于** tenantId=NULL。实际数据库中 auditor01 的 sys_user.tenant_id=6（属于租户 6），同时 platformPrincipal=true 标记为平台主体。这种情况下：
> - 已选活跃租户 → 走分支 A，activeTenantId 参与隔离
> - 未选活跃租户 → 走分支 B，tenantId=6 参与隔离（就是 auditor01 实际走的链路）
> 
> 参见第 15 章「平台主体透明适配模式」订正。

### Controller 调用模式

```java
// ✅ 写操作（必须传 ResourceScope，执行全三层）
public R<Void> update(@RequestBody SysRole sysRole) {
    SysRole exist = sysRoleService.getById(sysRole.getId());
    if (exist == null) return R.fail("角色不存在");
    // L1 租户归属 + L2 DataScope + L3 system:role:edit —— 一行搞定
    permissionGuard.check(ResourceScope.of(exist.getTenantId(), null, null),
                          "system:role:edit");
    ...
}

// ✅ 读操作（传 null 跳过 L2 主动校验，由 MP 拦截器 SQL 兜底）
public R<SysRole> getById(@PathVariable Long id) {
    SysRole role = sysRoleService.getById(id);
    if (role == null) return R.fail("角色不存在");
    // 只有 L1 租户归属校验，L2 由 SQL 自动注入，L3 无 perms 跳过
    permissionGuard.check(ResourceScope.of(role.getTenantId(), null, null));
    ...
}

// ❌ 禁止手写散落比对
// if (exist == null || !tenantId.equals(exist.getTenantId())) return R.fail(...);
```

### 4.3 双层并行：PermissionGuard 主动校验 + MP 拦截器 SQL 兜底

```
Controller 层 PermissionGuard.check() —— 前置主动校验，早失败
    ↓ 通过
Service 层 MP 拦截器链 —— SQL 级兜底
    TenantLineInnerInterceptor 追加 WHERE tenant_id = ? （最内层）
    DataPermissionInterceptor 追加 WHERE dept_id / create_by 条件（中层）
    ↓ 执行 SQL
数据库
```

两层互不替代：PermissionGuard 补的是「写操作 DataScope 主动校验」原来完全缺失的漏洞（SELF 范围用户改别人创建的记录，SQL 拦截器管不住入参）；MP 拦截器继续负责读操作的 SQL 过滤。

**实测边界区分：**

1. 普通租户跨租户写：TenantLine SQL 直接过滤，查询返回 null，**不会进入 PermissionGuard L1 租户归属校验**；对外表现记录不存在。
2. 只有 TenantLine 被 skip 放行的场景（主要是平台 admin tenantId=0），查询可以拿到其他租户的资源记录，才会走到 PermissionGuard L1 做租户归属判断；
3. 当前实现：平台 admin 在 PermissionGuard 入口整体跳过 L1/L2/L3 全部校验，因此 admin 可以直接修改其他租户业务数据。

## 5. PermissionGuard 与 CustomTenantHandler.skip 的边界

两者是**完全不同的机制**，不要混淆：

| 维度 | PermissionGuard L1 | CustomTenantHandler.skip() |
|---|---|---|
| 目的 | **执行时强制租户隔离**——不让跨租户操作通过 | **主动绕开租户隔离**——平台数据（tenant_id=0）让租户读到 |
| 调用方 | 业务 Controller 的权限守卫 | 业务 ServiceImpl 的跨租户读取场景 |
| 是否可逆 | 不可逆（拦截就是拦截） | 可逆（skip 后必须 finally reset） |
| 典型场景 | `PUT /tenant/role` → PermissionGuard 拦跨租户写 | `FormDefinitionService.getById()` → skip 让租户读 admin 创建的表单 |

## 7. 跨租户读取平台数据（CustomTenantHandler.skip 三行模式）

### 7.1 什么时候需要 skip？

平台 admin 创建的数据（`tenant_id=0`），租户用户通过关联引用需要读到时：

| 场景 | 举例 |
|---|---|
| 工作流关联的表单 | admin 创建 form_id=43，租户发起 definition.formDefinitionId=43 的流程 |
| 字典类型/字典数据 | admin 统一维护的字典，所有租户共享用 |
| 平台分发给租户的工作流 | admin 设计流程 definition 发布，租户用户发起 |
| 数据字典、枚举类配置 | 平台级配置，所有租户读同一份 |

### 7.2 标准三行模板（必须 finally reset！）

```java
CustomTenantHandler.skip();
try {
    FormDefinition def = formDefinitionService.getById(id);
    // 或 dictTypeService.list() / workflowNodeService.list() ...
} finally {
    CustomTenantHandler.reset();  // ⚠️ 一定要在 finally 里 reset！
}
```

### 7.3 已识别必须 skip 的接口清单

| 接口 | 类 | 原因 |
|---|---|---|
| `GET /form/definition/{id}` | FormDefinitionController | 工作流关联的表单可能是 admin 创建的 |
| `GET /form/definition/all-active` | FormDefinitionController | 工作流设计器下拉选关联表单 |
| `GET /form/field/list/{defId}` | FormFieldController | 同上，加载字段元数据 |
| `GET /workflow/definition/published` | WorkflowDefinitionController | 租户侧看到 admin 发布的流程 |
| `GET /workflow/definition/{id}` | WorkflowDefinitionController | 发起/编辑时读 definition + nodes |
| `WorkflowInstanceServiceImpl.resolveGatewayBranch()` | WorkflowInstanceServiceImpl | 网关分流时读 node.definitionId 的节点 |
| `WorkflowApproveServiceImpl.forwardToNextNode()` | WorkflowApproveServiceImpl | 审批推进时读 node |
| **`WorkflowNodeServiceImpl.listByDefinitionId()`** | WorkflowNodeServiceImpl | definition_id 全局唯一，不需要叠加 tenant_id；TenantLine 追加条件后查不全 |
| **`WorkflowNodeServiceImpl.batchSaveNodes()`** | WorkflowNodeServiceImpl | 内部先物理删除再批量插入；物理删除 SQL 被追加 `AND tenant_id=?` 会导致旧节点删不动，下次打开还在 |
| **`WorkflowNodeServiceImpl.deleteByDefinitionId()`** | WorkflowNodeServiceImpl | 软删场景同样被追加租户条件，删不掉跨租户节点 |
| **`PUT /auth/profile/password` 修改密码** | SysUserServiceImpl | 内部 getUserByUserName() 被 TenantLine 追加 activeTenantId 过滤 → 平台主体 tenantId=NULL 查不到自己 → 原密码永远校验失败；且 updateById 也被追加 tenant_id 过滤 → 更新 0 行 → **整个方法体包 skip/reset** |
| **平台侧 `PUT /system/user/{id}/reset-password`** | SysUserServiceImpl | 被重置用户 tenantId 不一定是 admin activeTenantId 能查到的 → TenantLine 追加后查不到 → **整个查询+更新+bumpVersion 包 skip/reset** |
| **`GET /auth/profile` / `GET /auth/userinfo` 获取个人资料** | AuthController → SysUserService | 查自己，TenantLine 可能过滤掉（同修改密码场景） → skip |

### 7.4 踩过的坑

| # | 坑 | 教训 |
|---|---|---|
| 1 | skip 了但忘了 reset → 后续所有 SQL 都跳过租户拦截 | **必须 finally reset**，哪怕前面 throw exception |
| 2 | 只在一个 ServiceImpl 里 skip → 另一个 ServiceImpl 同样的查询还是被拦截 | 网关分流在 **WorkflowInstanceServiceImpl 和 WorkflowApproveServiceImpl 两个类都有**，都要 skip |
| 3 | 不知道为什么 skip 了还是查不到 → definition 本身 tenantId 不是 0 | admin 创建的数据 tenant_id 是 0，其他租户是正数 |
| 4 | **TenantLineInnerInterceptor 对自定义 @Delete SQL 也追加 tenant_id** | MyBatis-Plus 拦截器链在 SQL 执行前统一改写，**不管是 MP 内置的 deleteById 还是 Mapper 接口上的 @Delete("DELETE FROM ...") 物理删除**，都会被追加 `AND tenant_id = ?`；不要以为物理删除绕过了 @TableLogic 就绕开了租户拦截，这是两个独立机制 |
| 5 | **全局唯一外键的子表不需要二次租户隔离** | wf_process_node.definition_id 全局唯一，一个节点通过 definition_id 就能精确归属到某个流程定义，再加 tenant_id 条件纯属多余且有害（租户侧登录时 tenantId 和节点表里的 tenantId 不匹配就会查不到/删不掉） |

### 7.5 历史脏数据兼容策略（2026-10-28 版本功能开发补充）

**问题**：wf_process_node 等业务子表历史数据 `tenant_id=0`（平台 admin 创建或旧代码未正确填充），租户侧登录时 TenantLine 自动追加 `AND tenant_id=当前租户ID` → 查不到节点、删不动节点、BPMN 预览纵向无连线。

**两种修法的对比**：

| 修法 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| ❌ 直接 skip() 绕过拦截器 | 所有读操作都不追加 tenant_id | 简单粗暴 | **破坏租户隔离**——任何租户都能读到其他租户的节点数据，P0 安全漏洞 |
| ✅ 兼容查询 + 按需 skip | ①物理删除/批量保存用 skip（definition_id 全局唯一，不怕跨租户）；②历史数据查询用 `tenant_id IN(?, 0)` 兼容；③新建流程 TenantMetaObjectHandler 自动填正确 tenantId | 既兼容历史脏数据，又不破坏租户隔离 | 查询条件多一个 IN 分支 |

**推荐组合（已落地）**：

```java
// ✅ 读操作（节点列表）：兼容历史脏数据，不 skip
LambdaQueryWrapper<WorkflowNode> w = new LambdaQueryWrapper<>();
w.eq(WorkflowNode::getDefinitionId, definitionId)
  .and(q -> q.eq(WorkflowNode::getTenantId, tenantId)
            .or()
            .eq(WorkflowNode::getTenantId, 0));  // 兼容历史脏数据

// ✅ 物理删除/批量保存：必须 skip（definition_id 全局唯一，跳过安全）
CustomTenantHandler.skip();
try {
    // deleteByDefinitionIdPhysical → DELETE FROM wf_process_node WHERE definition_id = ?
    // 不需要 tenant_id 条件也能精确定位
} finally {
    CustomTenantHandler.reset();
}

// ✅ 新建流程：让 TenantMetaObjectHandler 自动填正确 tenantId
// 不要手动 setTenantId()，拦截器 INSERT 时会覆盖成当前用户的 tenantId
```

### 7.6 跳过拦截器 vs 兼容查询的边界决策树

```
遇到租户侧查不到/删不动数据问题
    ↓
① 查 SQL：TenantLine 是不是追加了 tenant_id 条件？
    ↓ 是
② 业务表有 tenant_id 字段吗？
    ↓ 有
③ 表的主外键能精确归属资源吗？
    ↓ 是（如 wf_process_node.definition_id）
        → 物理删除/批量保存：✅ skip()，因为外键已经全局唯一
        → 读操作：✅ 兼容查询 tenant_id IN(?, 0)，不 skip（保护租户隔离）
    ↓ 否（如表单字段、普通业务表）
        → 读操作：❌ 不要 skip，加兼容 IN(?,0) 条件
        → 写操作：✅ 让 TenantMetaObjectHandler 自动填 tenantId
④ 表无 tenant_id 字段（全局共享表）
    → CustomTenantHandler 忽略表已配置，不需要 skip
```

### 7.7 skip 使用铁律三重申

| # | 铁律 | 违反后果 |
|---|------|----------|
| 1 | **skip 只用于物理删除/批量保存/全局外键唯一子表操作** | 读操作不 skip 才能保护租户隔离 |
| 2 | **skip 后必须 finally reset** | 异常时忘了 reset → 后续所有请求都 skip → 全租户数据泄露 |
| 3 | **skip 的范围要最小化** | 只包裹必须绕开的那几行 SQL，不要包裹整个方法 |

## 10. TenantMetaObjectHandler 自动填充约束

TenantMetaObjectHandler 在 INSERT/UPDATE 时自动填充 tenantId（INSERT 也填，以当前登录用户 tenantId 为准）。

### 10.1 优先级

```
TenantMetaObjectHandler 自动填充
    ↓ 优先于
业务代码手动 setTenantId()
    ↓ 即：手动 set 会被自动填充覆盖
```

### 10.2 约束

| # | 规则 | 原因 |
|---|------|------|
| 1 | **新增业务表不要手动 setTenantId** | 让拦截器管，手动设会被覆盖 |
| 2 | **update 时如果要保留原 tenantId** | 先 getById 取出原记录 tenantId，再 update；拦截器 UPDATE 也会填，但只影响 UPDATE SET tenant_id=? 的场景，MP 的 updateById 用的是从 DB 读出来的字段值，不会被篡改 |
| 3 | **listByIds + in 批量查绕过拦截** | MP 拦截器只在 Wrapper 上追加，in 条件直接传 ID 集合时不追加 → **禁止用 listByIds 跨租户查** |

## 13. 租户侧手机号登录流程（2026-10-30 落地）

### 13.1 接口变更

| 接口 | 变更 |
|---|---|
| `POST /tenant-auth/login` | `TenantLoginReq.username` → `phone`；`tenantId` 改为可选参数 |
| `GET /tenant-auth/tenant/list` | **彻底删除**（原来用于租户下拉列表，存在租户信息泄露风险） |

### 13.2 登录链路（匿名接口天然 skip TenantLine）

```
POST /tenant-auth/login (tenantId=null)
  ↓ TenantAuthServiceImpl.tenantLogin()
  ↓ tenantId == null → loginWithoutTenant()
  ↓ SELECT * FROM sys_user WHERE phone = ? AND tenant_id > 0
    ← 排除平台 admin（tenantId=0）
    AND del_flag = 0  ← @TableLogic 自动加的
  ↓ 批量查 sys_tenant → 过滤 status=0 且 expireDate > now → 有效租户
  ↓ 同一手机号 + 同一租户 → 多条记录？抛"账号异常"
  ↓ 遍历候选账号统一验密码：
    0 个匹配 → 抛"手机号或密码错误"
    1 个匹配 → buildLoginResponse → 直接返回 token
    ≥2 个匹配 → 返回 { step: "select-tenant", list: [TenantAccountVO] }
  ↓ 弹窗选租户 → 二次请求 POST /tenant-auth/login (tenantId=选中值)
  ↓ loginWithTenant() → 精确查 phone + tenantId → 验租户状态 → 验用户状态 → 验密码 → 返回 token
```

### 13.3 安全设计要点

| 设计 | 目的 |
|---|---|
| 二次请求必须重新验密码 | 防前端被篡改 tenantId 或抓包篡改 |
| 匿名接口 TenantLine 天然 skip | 登录查询需要跨租户匹配手机号 |
| 平台侧 /checkPhone 必须 skip TenantLine | admin 要给任意租户查手机号唯一性，TenantLine 默认 tenant_id=0 会查不到其他租户用户 |
| 后端 Controller 兜底校验 | 即使绕过前端直接 curl 调 add/update，后端也做手机号唯一性检查 |

**判断标准**：表有 tenant_id 字段 → 不在忽略表；表是全局共享的关联/配置表 → 在忽略表。

## 14. CustomTenantHandler 三层判断铁律（2026-10-30 补录）

### 13.1 tenantId 的三种状态

| tenantId 取值 | 来源 | ignoreTable() 行为 | SQL 行为 | skip() 必要性 |
|---|---|---|---|---|
| `null` | 匿名接口（未登录） | resolveTenantId() 返回 null → skip=true | 不追加 `WHERE tenant_id=?` | ❌ 不需要（天然 skip） |
| `0` | 平台 admin 登录 | tenantId==0 → return true（硬编码特殊处理） | 不追加 `WHERE tenant_id=0` | ❌ 不需要（天然 skip） |
| `>0` | 普通租户登录 | return false | 追加 `WHERE tenant_id=当前租户ID` | ✅ 跨租户查询时必须 skip |

> **这三条是 CustomTenantHandler 的核心逻辑，任何时候写跨租户 SQL 前先对着表判断 tenantId 取值。**

### 13.2 admin 天然 skip，但平台主体不天然

❌ **旧认知（已纠正）**："admin 不需要 skip，所以所有场景都不需要 skip"——这是不对的。admin（tenantId=0）天然 skip，但**平台主体（tenantId=NULL 或 >0 + platformPrincipal=true）不天然 skip**，activeTenantId 会让 TenantLine 追加 `WHERE tenant_id = activeTenantId`。

✅ **正确区分**：
```
admin（tenantId=0）：天然 skip TenantLine → 一般不需要手动 skip
  但 resetPassword 平台侧重置任意用户 → 被重置用户 tenantId 不是 0 → 追加 tenant_id=0 查不到 → 需要 skip

平台主体（platformPrincipal=true + 可能有 activeTenantId）：不天然 skip
  修改密码 → TenantLine 追加 activeTenantId → 查不到自己 → 需要 skip
  平台侧重置任意用户 → 同上 → 需要 skip

普通租户（tenantId>0）：不天然 skip
  跨租户读 admin 表单 → 需要 skip
```

### 13.3 真正需要 skip 的场景

| 场景 | 操作方 | 原因 |
|---|---|---|
| 表单设计器读 admin 创建的 form_definition | 租户用户（tenantId=6） | form_definition.tenant_id=0（admin 建的），TenantLine 追加 `WHERE tenant_id=6` 查不到 |
| 工作流节点物理删除 | 租户用户 | definition_id 全局唯一，TenantLine 追加 tenant_id 条件会导致删不动 |
| 平台管理员手机号唯一性校验 | admin（tenantId=0） | 虽然 admin 天然 skip，但手动构造 wrapper 加 tenantId 精确过滤时，skip 包一层是防御性编程 |
| **平台/租户侧修改密码（changePassword）** | 平台主体 / 租户用户 | 内部 getUserByUserName() 被 TenantLine 追加 activeTenantId 过滤，auditor01 tenantId=NULL 时查不到自己 → 整个方法体包 skip/reset |
| **平台侧重置任意用户密码（resetPassword）** | admin / 平台主体 | 被重置用户 tenantId 不是 0/activeTenantId，TenantLine 追加后查不到 → 整个查询+更新+bumpVersion 包 skip |
| **AuthController.getUserInfo / getCurrentUserProfile** | 所有用户 | 查自己，TenantLine 可能过滤掉（同修改密码场景） → skip |

### 13.4 嵌套 skip/reset 是破坏性的
外层 skip() → flag = true 内层 fillDeptName.skip() → flag = true（幂等） 内层 fillDeptName.reset() → flag = false ← 💥 把外层也清了！ 后续 SQL 不再 skip → TenantLine 拦截 外层 reset() → flag = false（已经是 false，没用）

**规则**：skip 必须最小化包裹范围，不要嵌套。如果一个方法里有多个独立的 skip 需求，可以：
- 要么每个 SQL 语句前后各 skip-reset 一次
- 要么外层包一层，内层方法里的 skip/reset 删掉

## 15. 平台主体透明适配模式（2026-11-08 落地 + 2026-11-10 Scope 改造补录）

> 平台主体（platformPrincipal）是跨租户审计账号，登录时 tenantId=NULL，通过 activeTenantId 选择活跃租户后，整条链路的租户隔离与普通租户用户**完全一致**，业务代码零改动。

### 15.1 三字段状态

| 字段 | 取值范围 | 语义 |
|---|---|---|
| `LoginUser.tenantId` | **NULL 或 >0** | 平台主体 sys_user.tenant_id **可能是 NULL 也可能是某个租户 ID**，取决于创建时的分配方式（auditor01 实际是 tenant_id=6） |
| `LoginUser.platformPrincipal` | **true** | 标记这是平台控制面主体 |
| `LoginUser.activeTenantId` | **已选租户ID / null** | 选租户后通过换发 token 写入 JWT claim，**getUserInfo() 必须从 JWT 解析 set 到 LoginUser**（2026-11-08 新增约束，之前漏掉导致前端永远拿不到） |

> **超管 admin 对比**：tenantId=0，platformPrincipal=null/false，不需要选租户，天然跳过所有租户拦截。
>
> **2026-11-07 踩坑订正**：之前假设平台主体 tenantId=NULL，但实际 auditor01 是 tenantId=6 + platformPrincipal=true。这个差异直接决定 PermissionGuard 走分支 A 还是分支 B——**但两条分支都已加审计**，都能正确触发 CROSS_TENANT_ACCESS 日志。
>
> **2026-11-08 踩坑订正**：LoginUser 每次加新字段 → getUserInfo() 必须同步从 JWT claim 里解析 set，否则前端 store.userInfo 里没有这个字段。activeTenantId 在 JWT payload 里存在，但之前 getUserInfo() 忘了 set → 前端永远 fallback 默认值。

### 15.2 拦截器链优先级 0 适配（CustomTenantHandler 源码已实现）

```java
// resolveTenantId() 优先级 0 → 直接返回 activeTenantId
if (loginUser != null && Boolean.TRUE.equals(loginUser.getPlatformPrincipal())
        && loginUser.getActiveTenantId() != null) {
    return loginUser.getActiveTenantId();
}
```

TenantLineInnerInterceptor 据此自动追加 `WHERE tenant_id = activeTenantId`，与普通租户用户行为完全一致。

### 15.3 SecurityUtils 透明入口（全项目零改动）

```java
public static Long getTenantId() {
    LoginUser loginUser = getLoginUser();
    // 平台主体已选活跃租户 → 优先返回 activeTenantId
    if (Boolean.TRUE.equals(loginUser.getPlatformPrincipal())
            && loginUser.getActiveTenantId() != null) {
        return loginUser.getActiveTenantId();
    }
    return loginUser.getTenantId();
}
```

全项目 28+ 处业务代码调用此方法，平台主体选租户后自动正确过滤。任何需要区分主体类型的底层组件（PermissionGuard / CustomTenantHandler 自身）必须用 `SecurityUtils.getPrincipalTenantId()` 取原始值。

### 15.4 ⚠️ skip 对所有主体生效的破坏性边界

`CustomTenantHandler.skip()` 是 ThreadLocal 开关，**对普通租户、平台主体、超管三种主体全部生效**。

```
❌ 误用场景（本次 auditor01 漏洞根因）：
SysUserController.list() 加 skip() → 原本只考虑 admin 跨租户查询
→ 但平台主体/普通租户 skip 后同样失去租户隔离
→ 前端不传 tenantId 参数 → 查出全租户数据
```

**规则**：skip 后**必须**手动补 tenantId 过滤条件，不能依赖 TenantLine 自动追加。

### 15.5 列表接口 skip 后 tenantId 自动注入模板（强制）

```java
CustomTenantHandler.skip();
try {
    LambdaQueryWrapper<SysUser> wrapper = new LambdaQueryWrapper<>();
    // ⭐ skip 后租户过滤三档决策：
    Long effectiveTenantId = tenantId;  // 先取前端传入参数
    if (effectiveTenantId == null) {
        Long ctxTenantId = SecurityUtils.getTenantId();
        // tenantId=0 或 null → 不注入（超管查全部 / 无上下文）
        // tenantId>0 → 自动注入（普通租户 / 平台主体已选活跃租户）
        if (ctxTenantId != null && ctxTenantId > 0) {
            effectiveTenantId = ctxTenantId;
        }
    }
    if (effectiveTenantId != null) {
        wrapper.eq(SysUser::getTenantId, effectiveTenantId);
    }
    // ... 其余 wrapper 条件 + page 查询
} finally {
    CustomTenantHandler.reset();
}
```

### 15.6 修改密码等「查自己」场景也需要 skip

**问题**（2026-11-07 auditor01 修改密码始终提示「原密码错误」）：

```
SysUserServiceImpl.changePassword()
  → getUserByUserName() → 被 TenantLine 追加 WHERE tenant_id = activeTenantId(6)

## 16. PermissionGuard 审计日志机制（2026-11-07 落地）

### 16.1 四种审计 actionType 与触发位置

| actionType | 触发场景 | 写入位置 |
|---|---|---|
| `SWITCH_TENANT` | 平台主体切换活跃租户 | AuthController.switchTenant() |
| `SCOPE_ASSIGN` | 平台超管分配 Scope 给平台主体 | PrincipalScopeController.assignScopes() |
| `SCOPE_REVOKE` | 平台超管撤销 Scope | 走 assignScopes 传空列表（actionType 记为 SCOPE_ASSIGN） |
| **`CROSS_TENANT_ACCESS`** | **平台主体执行跨租户写操作** | PermissionGuard.checkTenantIsolation() |

### 16.2 CROSS_TENANT_ACCESS 审计触发条件（精准）

```
① 主体必须是平台主体（platformPrincipal=true）
   → admin 从 doCheck 入口直接 return，不进 PermissionGuard
   → 普通租户用户不审计（正常业务行为）

② 必须是写操作（targetScope.targetTenantId != null）
   → 读操作（targetTenantId == null）不审计，避免列表查询导致日志膨胀

③ L1 校验通过后（scopeAllowed 或 tenantId 归属比对通过）才写
   → 403 拒绝的操作不写审计（没有实际执行）

④ 静默降级：try-catch 包裹，审计失败不阻断主业务
```

### 16.3 审计覆盖矩阵

| 主体类型 | 分支 | 写操作审计 | 目标租户来源 |
|---|---|---|---|
| 平台主体 + 已选活跃租户 | A | ✅ | activeTenantId |
| 平台主体 + 未选活跃租户（但 tenantId>0） | B | ✅ | 原始 tenantId |
| 普通租户用户（非平台主体） | B | ❌ 不审计 | - |
| 超管 admin | 入口 return | ❌ 不审计 | - |

## 17. 新建（add）场景的 PermissionGuard 调用模式（2026-11-07 补全）

### 17.1 之前的问题

**7 个核心系统 Controller 的 add() 方法完全没有调用 PermissionGuard！** update/delete 都走三层校验链，但新建只靠 `@RequiresPermission` AOP 做按钮权限校验——**L1 租户隔离 + L2 DataScope 主动校验完全缺失**。

```
后果：
① 平台主体可以绕过 L1，在任意租户下新建用户/角色/部门
② 平台主体可以绕过 L2 DataScope，在自己不可见的部门下新建资源
③ 新建操作不触发 CROSS_TENANT_ACCESS 审计日志
```

### 17.2 新建场景 ResourceScope 构造模式

新建场景没有「已存在的目标资源」（getById 返回 null），所以用**预期值**代替：

```java
// 租户侧 Controller（tenantId 从 JWT token 自动注入）
public R<Long> add(@RequestBody SysUser sysUser) {
    // ⭐ 新建场景 PermissionGuard：用预期目标值构造 ResourceScope
    permissionGuard.check(
        ResourceScope.of(
            tenantId,                           // targetTenantId：预期归属租户
            sysUser.getDeptId(),                // targetDeptId：预期归属部门
            SecurityUtils.getUsername()         // targetCreateBy：预期创建人（String，从 SecurityUtils 取）
        ),
        "system:user:add"
    );
    // ... save
}

// 平台侧 Controller
public R<Long> add(@RequestBody SysUser sysUser) {
    permissionGuard.check(
        ResourceScope.of(
            sysUser.getTenantId(),              // targetTenantId：前端传入的租户
            sysUser.getDeptId(),                // targetDeptId
            SecurityUtils.getUsername()         // targetCreateBy（注意是 getUsername() 小写 u）
        ),
        "system:user:add"
    );
    // ... save
}
```

### 17.3 ResourceScope 三参数类型铁律（不能错！）

| 参数 | 类型 | 来源 | 说明 |
|---|---|---|---|
| targetTenantId | **Long** | 前端传入 / 从 token 取 | L1 租户归属比对用 |
| targetDeptId | **Long** | 前端传入的 deptId / parentId | L2 DEPT/DEPT_AND_CHILD/CUSTOM 范围校验用 |
| targetCreateBy | **String** | `SecurityUtils.getUsername()` | L2 SELF 范围校验用（**注意是 String 用户名，不是 Long userId**） |

> ⚠️ **2026-11-07 编译错误踩坑**：之前误用了 Long userId 作为 targetCreateBy，ResourceScope.of 签名是 `(Long, Long, String)` → 编译报 `incompatible types: java.lang.Long cannot be converted to java.lang.String`。
> 
> 另：`SecurityUtils.getUsername()`（小写 u，工具类静态方法）≠ `LoginUser.getUserName()`（大写 U，实体 getter）。

## 18. 平台主体 Scope 角色绑定改造完整链路（2026-11-10 P0 落地）

> 核心目标：平台主体在每个租户下可独立绑定一个租户角色（**userId + tenantId + roleId 三元绑定**），不侵入 sys_user_role、不改 PermissionGuard/RBAC 核心逻辑、不改动已稳定的两步式登录链路。

### 18.1 数据库 DDL（已手动执行）

### 18.3 权限链路重载（根因：JwtAuthenticationFilter 时序问题）

**根本问题**：JwtAuthenticationFilter 链内执行顺序为：
```

                                                        ↑

**修法**：PermissionService / SysMenuService **新增显式传参重载**，Filter 把 JWT 已解析的参数直接传入，不再依赖 SecurityContext。

```java

// ✅ 旧单参数方法保留（给 Controller/ServiceImpl 里正常业务代码用）

// 内部：从 SecurityUtils 取参数 → 委托新重载
```

**SysMenuService 同样模式**：

// 旧单参数方法 → 从 SecurityUtils 取 → 委托新重载

### 18.5 权限缓存租户维度隔离（P0 修复：循环覆盖根因）

**旧缓存 key（单维度）**：`rbac:perms:{userId}` —— 同一用户多个租户权限互相覆盖。

**新缓存 key（租户维度）**：`rbac:perms:{userId}:{effectiveTenantId}`

public void clearPermCache(Long userId, Long effectiveTenantId) {
    // 精确删除指定租户维度
    String key = "rbac:perms:" + userId + ":" + effectiveTenantId;
    redis.delete(key);
    // 批量删除全部租户维度（角色变更等跨租户写操作时）
    redis.delete(keys("rbac:perms:" + userId + ":*"));
}
```

### 18.6 隐性约束清单（本次改造发现）

| # | 约束 | 违反后果 |
|---|------|----------|
| I1 | **principal_tenant_scope 所有读写操作必须 skip + try-finally reset** | TenantLine 追加 tenant_id 条件 → 查不全旧记录 / 删不动 → 重复数据残留 |
| I2 | **role_id 字段允许 NULL，历史数据不迁移** | 若强制非 NULL，老主体账号必须手动补角色绑定才能恢复权限 |
| I3 | **角色下拉必须三重校验**：① 归属租户匹配 role.tenantId = 当前行 tenantId ② roleKey ≠ admin ③ role.status = 启用 | 超管角色不应出现在 Scope 绑定选项；禁用角色不可选 |
| I4 | **scope_role_merge 查询必须 skip** | 平台主体 activeTenantId 下查 sys_role_menu → TenantLine 可能过滤掉平台侧角色（platform role tenantId=0） |
| I5 | **resolveEffectiveTenantId 方法必须同时接受 activeTenantId + platformPrincipal 参数** | 只从 SecurityUtils 取 → JwtAuthenticationFilter 时序问题下永远拿不到 |
| I6 | **filterByTenantMenuPool 必须用传入的 activeTenantId，不能从 SecurityUtils 取** | 同上时序问题 |
| I7 | **JwtAuthenticationFilter 内 PermissionService/SysMenuService 调用必须走显式传参重载** | 走旧单参数方法 → SecurityUtils.getLoginUser()=null → 返回空权限 → 全部 403 |
| I8 | **缓存清理必须用租户维度 key** | 只清 `rbac:perms:{userId}` → 另一租户权限仍被覆盖过的脏值 → 循环覆盖复现 |
| I9 | **clearPermCache 必须双模式**（精确删一个租户 + 批量删全部租户） | 角色变更（跨租户影响）时只删当前租户 → 另一租户缓存还是旧的 |
| I10 | **principal_tenant_scope 不可加 TenantLine 忽略表配置** | 全局关联表，但每条记录带 tenantId（被绑定的租户），需要按 tenantId 过滤普通业务查询场景 |
| I11 | **@TableName + ServiceImpl 继承链必须完整** | PrincipalTenantScopeServiceImpl 必须继承 `ServiceImpl<PrincipalTenantScopeMapper, PrincipalTenantScope>`，手动注入 mapper 绕过继承会导致 getEntityClass() 抽象方法未实现 |
| I12 | **PermissionGuard / JwtAuthenticationFilter 两处 platformPrincipal 判断逻辑必须同步** | 前者用 `Boolean.TRUE.equals(loginUser.getPlatformPrincipal())`，后者用 `userClaim.getBoolean("platformPrincipal", false)`，两边取值不一致会导致一条链路走 scope 合并、另一条不走 |

## 19. 租户内经营单元（BizUnit）视图切换体系（2026-11-11 P0 落地）

> **核心定位**：经营单元（BizUnit）是**租户内部的软视图标识**，不参与底层租户拦截逻辑，不能替代租户 ID，不能作为租户隔离条件。与 §18 平台主体跨租户 Scope **完全隔离、互不耦合**。
> 
> **对齐范式**：100% 复用 §18 PrincipalTenantScope 的「先删后插事务、skip+try-finally reset、IGNORED_TABLES 中间表」整套实现范式。

### 19.1 设计目标（红线约束）

| # | 约束 | 违反后果 |
|---|------|----------|
| R1 | **经营单元仅为租户内软视图，不参与租户隔离** | 如果让 bizUnit 当 tenant_id 用 → 底层 TenantLine 语义混乱 |
| R2 | **与平台主体 Scope 两套链路完全隔离** | PrincipalTenantScope 是跨租户主体账号的事，BizUnit Scope 是租户内普通用户的事，互不干扰 |
| R3 | **平台主体账号完全禁用经营单元能力** | `platformPrincipal=true` → `/tenant/biz-unit/*` 全部 403 |
| R4 | **BizUnit 切换不改变租户归属** | sys_user.tenant_id 始终不变，activeBizUnitId 只是 JWT 里的可选 claim |
| R5 | **DataScope 覆盖模式在 BizUnit 激活时接管** | 普通角色的 dataScope（DEPT/DEPT_AND_CHILD/SELF/CUSTOM）被跳过，改用「经营单元自身 + 全部下级部门」构造 IN 列表 |

  最终 roleIds = sys_user_role（原始角色）
              ∪ sys_biz_unit_scope.where(userId=当前 AND bizUnitId=选中).roleId

平台主体（任何 activeBizUnitId 都不生效）：
  最终 roleIds = sys_user_role（平台侧角色）
              ∪ principal_tenant_scope.where(userId=当前 AND tenantId=activeTenantId).roleId
  → 不触发 BizUnit Scope 合并
```

|---|------|------|------|----------|
| 1 | GET | `/tenant/biz-unit/tree` | 经营单元树形（全部门，节点带 isBizUnit 标记） | 平台主体 → 403 |

**PUT /tenant/biz-unit/switch 换发 token 流程**：
```
1. 校验：用户已绑定目标经营单元 → 403 未绑定
2. regenerateToken(oldToken, user, newBizUnitId)
   ├─ 查角色（双 skip 保护）：sys_user_role 原始角色
   ├─ 合并 BizUnit 绑定角色（双 skip 保护）：sys_biz_unit_scope.roleId
   ├─ JwtUtil.createToken() → activeBizUnitId=newBizUnitId, 其它 claim 全保留
   └─ RefreshTokenService 四参数 → 完整透传
3. 返回 { accessToken, activeBizUnitId }
```

### 19.11 标准双 skip 模板（2026-11-11 固化范式）

```java
// ✅ 正确：双 skip + try-finally + reset 顺序相反
CustomTenantHandler.skip();      // ① 先跳租户拦截
DataScopeContext.skip();          // ② 再跳数据权限拦截
try {
    User user = userService.getById(userId);  // 任何 ServiceImpl 调用
    Role role = roleService.getById(roleId);
    // ...
} finally {
    DataScopeContext.reset();      // ③ 先清数据权限（和 skip 顺序相反）
    CustomTenantHandler.reset();    // ④ 后清租户拦截
}

// ❌ 错误：只 skip 一个
DataScopeContext.skip();
try {
    userService.getById(userId);  // TenantLine 还在！追加 tenant_id=? 可能过滤掉
} finally {
    DataScopeContext.reset();
}

// ❌ 错误：reset 顺序反了
// skip: CustomTenantHandler → DataScopeContext
// reset: CustomTenantHandler → DataScopeContext（反了！）
// 后果：CustomTenantHandler.reset() 先执行 → 后续 SQL TenantLine 又生效 → 静默过滤
```

### 19.13 踩坑复盘（2026-11-11 实际发生）

| # | 现象 | 根因定位 | 修复 |
|---|------|----------|------|
| P1 | 切换成功后新 token 调 getUserInfo 报「用户不存在」 | 只 skip 了 TenantLine，没 skip DataScope → Handler 触发 doBizUnitOverride → sys_user 被追加 dept_id IN (...) → 用户不在列表 → 返回空 | **双 skip 范式**，影响 AuthController / PermissionServiceImpl / Controller 共 11 处 |
