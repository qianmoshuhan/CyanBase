# 租户底座
---
## 1. 多租户拦截器链
**TenantMybatisPlusConfig.java** 注册三层拦截器链（顺序不能反）：
```
外层（先执行）：PaginationInnerInterceptor     → 分页 / 物理删除
中层（后执行）：DataPermissionInterceptor       → 追加 dept_id / create_by 过滤（@DataScope）
内层（最后执行）：TenantLineInnerInterceptor    → 追加 tenant_id 过滤
```

TenantLineInnerInterceptor 必须最后执行，否则分页 SQL 里的租户条件会被分页器当成业务条件。

```java
@Bean(name = "tenantMybatisPlusInterceptor")
@Primary
public MybatisPlusInterceptor tenantMybatisPlusInterceptor(...) {
    MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
    interceptor.addInnerInterceptor(new PaginationInnerInterceptor());          // 外层
    interceptor.addInnerInterceptor(dataPermissionInterceptor);                 // 中层
    interceptor.addInnerInterceptor(new TenantLineInnerInterceptor(handler));   // 内层
    return interceptor;
}
```

> ⚠️ 必须加 @Primary，否则 MyBatis-Plus 自动配置找不到哪个 Bean 要用。

## 3. 租户侧和平台侧共用一套 perms

```java
// ❌ 错误：租户侧造新权限
@RequiresPermission("tenant:role:add")  // DB 里根本没有这条！

// ✅ 正确：租户侧和平台侧用同一套
@RequiresPermission("system:role:add")
```

两套 Controller → 一套 sys_menu perms，sys_menu 是共享表。

## 4. 多租户 SQL 自动注入

TenantLineInnerInterceptor 在所有 INSERT / UPDATE / DELETE / SELECT 的 WHERE 里自动追加：

```sql
WHERE ... AND tenant_id = 当前用户的 tenantId
```

**例外**：SysTenantController（租户管理本身）、超管用户（tenantId=0）、显式排除的表。

## 4. PermissionGuard L1：租户硬隔离主动校验

> 2026-10-23 落地。原来散放在 TenantRoleController（7处）/ TenantUserController（5处）/ TenantDeptController（2处）里的 `tenantId.equals(exist.getTenantId())` 租户归属比对，已全部统一到 PermissionGuard 的 L1 层。

### 4.1 L1 校验逻辑（不可拆分）

```
步骤 1.1  登录态：userId != null → 401 "请先登录"
步骤 1.2  身份：必须是租户用户（tenantId > 0）OR 平台超管（username="admin"）
         → 否则 403 "非租户用户无权访问租户接口"
步骤 1.3  资源归属（仅 targetScope.targetTenantId != null 时比对）
         超管跳过；否则 currentTenantId == targetTenantId
         → 否则 403 "无权操作其他租户的数据"
```

### 4.2 Controller 调用模式

```java
// ✅ 写操作（必须传 ResourceScope，执行全三层）
public R<Void> update(@RequestBody SysRole sysRole) {
    SysRole exist = sysRoleService.getById(sysRole.getId());
    if (exist == null) return R.fail("角色不存在");
    // L1 租户归属 + L2 DataScope + L3 system:role:edit —— 一行搞定
    permissionGuard.check(ResourceScope.of(exist.getTenantId(), null, null),
                          "system:role:edit");
    ...
}

// ✅ 读操作（传 null 跳过 L2 主动校验，由 MP 拦截器 SQL 兜底）
public R<SysRole> getById(@PathVariable Long id) {
    SysRole role = sysRoleService.getById(id);
    if (role == null) return R.fail("角色不存在");
    // 只有 L1 租户归属校验，L2 由 SQL 自动注入，L3 无 perms 跳过
    permissionGuard.check(ResourceScope.of(role.getTenantId(), null, null));
    ...
}

// ❌ 禁止手写散落比对
// if (exist == null || !tenantId.equals(exist.getTenantId())) return R.fail(...);
```

### 4.3 双层并行：PermissionGuard 主动校验 + MP 拦截器 SQL 兜底

```
Controller 层 PermissionGuard.check() —— 前置主动校验，早失败
    ↓ 通过
Service 层 MP 拦截器链 —— SQL 级兜底
    TenantLineInnerInterceptor 追加 WHERE tenant_id = ? （最内层）
    DataPermissionInterceptor 追加 WHERE dept_id / create_by 条件（中层）
    ↓ 执行 SQL
数据库
```

两层互不替代：PermissionGuard 补的是「写操作 DataScope 主动校验」原来完全缺失的漏洞（SELF 范围用户改别人创建的记录，SQL 拦截器管不住入参）；MP 拦截器继续负责读操作的 SQL 过滤。

## 5. PermissionGuard 与 CustomTenantHandler.skip 的边界

两者是**完全不同的机制**，不要混淆：

| 维度 | PermissionGuard L1 | CustomTenantHandler.skip() |
|---|---|---|
| 目的 | **执行时强制租户隔离**——不让跨租户操作通过 | **主动绕开租户隔离**——平台数据（tenant_id=0）让租户读到 |
| 调用方 | 业务 Controller 的权限守卫 | 业务 ServiceImpl 的跨租户读取场景 |
| 是否可逆 | 不可逆（拦截就是拦截） | 可逆（skip 后必须 finally reset） |
| 典型场景 | `PUT /tenant/role` → PermissionGuard 拦跨租户写 | `FormDefinitionService.getById()` → skip 让租户读 admin 创建的表单 |

### 4.4 踩坑避坑表（增量）

| # | 坑根因 | 教训 |
|---|--------|------|
| 6 | TenantDeptController.update 原来完全没有主动校验，只靠 MP 兜底 | 写操作一律 PermissionGuard.check(ResourceScope, ...)，不能漏 |
| 7 | ResourceScope.of(tenantId, null, null) targetDeptId=null → L2 DEPT/DEPT_AND_CHILD 放通（无维度信息） | ResourceScope 三参数：targetTenantId（L1 用）+ targetDeptId（L2 DEPT/DEPT_AND_CHILD/CUSTOM 用）+ targetCreateBy（L2 SELF 用），按需传 null |

## 7. 跨租户读取平台数据（CustomTenantHandler.skip 三行模式）

### 6.1 什么时候需要 skip？

平台 admin 创建的数据（`tenant_id=0`），租户用户通过关联引用需要读到时：

| 场景 | 举例 |
|---|---|
| 工作流关联的表单 | admin 创建 form_id=43，租户发起 definition.formDefinitionId=43 的流程 |
| 字典类型/字典数据 | admin 统一维护的字典，所有租户共享用 |
| 平台分发给租户的工作流 | admin 设计流程 definition 发布，租户用户发起 |
| 数据字典、枚举类配置 | 平台级配置，所有租户读同一份 |

### 6.2 标准三行模板（必须 finally reset！）

```java
CustomTenantHandler.skip();
try {
    FormDefinition def = formDefinitionService.getById(id);
    // 或 dictTypeService.list() / workflowNodeService.list() ...
} finally {
    CustomTenantHandler.reset();  // ⚠️ 一定要在 finally 里 reset！
}
```

### 6.3 已识别必须 skip 的接口清单

| 接口 | 类 | 原因 |
|---|---|---|
| `GET /form/definition/{id}` | FormDefinitionController | 工作流关联的表单可能是 admin 创建的 |
| `GET /form/definition/all-active` | FormDefinitionController | 工作流设计器下拉选关联表单 |
| `GET /form/field/list/{defId}` | FormFieldController | 同上，加载字段元数据 |
| `GET /workflow/definition/published` | WorkflowDefinitionController | 租户侧看到 admin 发布的流程 |
| `GET /workflow/definition/{id}` | WorkflowDefinitionController | 发起/编辑时读 definition + nodes |
| `WorkflowInstanceServiceImpl.resolveGatewayBranch()` | WorkflowInstanceServiceImpl | 网关分流时读 node.definitionId 的节点 |
| `WorkflowApproveServiceImpl.forwardToNextNode()` | WorkflowApproveServiceImpl | 审批推进时读 node |

### 6.4 踩过的坑

| # | 坑 | 教训 |
|---|---|---|
| 1 | skip 了但忘了 reset → 后续所有 SQL 都跳过租户拦截 | **必须 finally reset**，哪怕前面 throw exception |
| 2 | 只在一个 ServiceImpl 里 skip → 另一个 ServiceImpl 同样的查询还是被拦截 | 网关分流在 **WorkflowInstanceServiceImpl 和 WorkflowApproveServiceImpl 两个类都有**，都要 skip |
| 3 | 不知道为什么 skip 了还是查不到 → definition 本身 tenantId 不是 0 | admin 创建的数据 tenant_id 是 0，其他租户是正数 |

## 7. RBAC 缓存与 Redis Key

### 7.1 缓存键命名

| Key | 含义 |
|---|---|
| `rbac:perms:{tenantId}:{userId}` | 用户权限字符串集合（`Set<String>`） |
| `rbac:menu:{tenantId}:{userId}` | 用户菜单树（序列化的 List） |
| `rbac:roles:{tenantId}:{userId}` | 用户角色集合 |

### 7.2 缓存失效时机

- 角色-菜单关联变了（sys_role_menu INSERT/DELETE）→ 必须 DEL `rbac:perms:*`
- 用户-角色关联变了（sys_user_role INSERT/DELETE）→ 必须 DEL 该用户的 `rbac:perms:{tenantId}:{userId}`

### 7.3 一个常见 Bug

```sql
-- 给租户管理员加了新权限后
INSERT INTO sys_role_menu(role_id, menu_id, tenant_id) VALUES (15, 100, 6);

-- ❌ 忘了清缓存 → 刷新前端还是看不到菜单
-- ✅ Redis: DEL rbac:perms:* rbac:menu:*
```
