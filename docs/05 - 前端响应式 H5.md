## 1. 约束规则：全局隐性约束（改任何页面前先看这 5 条） [R]

| # | 约束 | 说明 |
|---|------|------|
| 1 | **viewport meta 必须存在** | `<meta name="viewport" content="width=device-width, initial-scale=1.0, maximum-scale=1.0, user-scalable=no">`，否则手机自动缩放错位 |
| 2 | **断点统一用 768px** [R] | `window.innerWidth <= 768`，Element Plus 栅格也是 768 分界 |
| 3 | **Element Plus 布局用 v-if 不用 v-show** | v-show 在 display:none 时组件内部 ref 会 null |
| 4 | **isMobile 检测加 resize 监听 + onBeforeUnmount 清理** | 只写 onMounted 一次不够 |
| 5 | **Vue 3 template 自动解包 ref** | template 里写 `{{ profile?.name }}` 不是 `profile.value?.name` |

### isMobile 标准模板

```typescript
const isMobile = ref(false)
const checkMobile = () => { isMobile.value = window.innerWidth <= 768 }
onMounted(() => { checkMobile(); window.addEventListener('resize', checkMobile) })
onBeforeUnmount(() => window.removeEventListener('resize', checkMobile))
```

## 4. 执行流程：分页最佳实践（完整代码模板）

👉 参考：00-README.md [约束 #7] 全局分页显式 handlePageChange 铁律

### ❌ 错误写法

```vue
<el-pagination @current-change="fetchList" />
<script>
const fetchList = async () => {
  const params = { pageNum: query.pageNum, ... }  // ⚠️ 读到的还是旧值
}
</script>
```

某些 Element Plus 版本中 `@current-change` 事件先于 `v-model:page-num` 的 `update` emit 执行，fetchList() 里读到的 pageNum 还是旧值，翻页永远请求 page1。

### ✅ 正确写法（显式回调，先赋值后请求）

```vue
<el-pagination
  v-model:page-num="query.pageNum"
  v-model:page-size="query.pageSize"
  @current-change="handlePageChange"
  @size-change="handleSizeChange"
/>
<script>
const query = reactive({ pageNum: 1, pageSize: 10, status: '', keyword: '', timeRange: [] })

// ⭐ 显式回调
const handlePageChange = (page) => {
  query.pageNum = page   // ① 先强制更新
  fetchList()            // ② 再请求（此时读 query.pageNum 一定是新值）
}
const handleSizeChange = (size) => {
  query.pageSize = size
  query.pageNum = 1      // 改条数必须重置第 1 页
  fetchList()
}
const handleSearch = () => { query.pageNum = 1; fetchList() }
const resetQuery = () => { query.keyword = ''; query.status = ''; query.timeRange = []; query.pageNum = 1; fetchList() }

const fetchList = async () => {
  const params = { pageNum: query.pageNum, pageSize: query.pageSize }
  if (query.status) params.status = query.status
  if (query.keyword?.trim()) params.keyword = query.keyword.trim()
  if (query.timeRange?.length === 2) {
    params.startTime = query.timeRange[0] + ' 00:00:00'
    params.endTime   = query.timeRange[1] + ' 23:59:59'
  }
  const res = await api.getList(params)
  list.value = res.data?.records || []
  total.value = res.data?.total || 0
}
</script>
```

### 适用场景

| 场景 | 关键动作 | 重置到第 1 页？ |
|---|---|---|
| 翻页 | handlePageChange(page) | ❌ 不重置 |
| 改每页条数 | handleSizeChange(size) | ✅ 必须重置 |
| 点击搜索 | handleSearch() | ✅ 必须重置 |
| 点击重置 | resetQuery() | ✅ 必须重置 |
| el-select 自动搜索 | 绑定回调里重置 pageNum=1 | ✅ 必须重置 |

### 跨页连续序号

```vue
<el-table-column
  type="index" label="序号" width="70"
  :index="(i) => (query.pageNum - 1) * query.pageSize + i + 1"
/>
```

el-table 原生 `type="index"` 默认不跨页连续，用函数形式手动计算。

## 5. 核心定义：后端分页接口规范（Java 侧示例）

> 前端分页最佳实践的后端配套，让分页链路完整闭环。

```java
@GetMapping("/list")
public R<Page<Xxx>> list(
        @RequestParam(defaultValue = "1") Integer pageNum,
        @RequestParam(defaultValue = "10") Integer pageSize,
        @RequestParam(required = false) String status,
        @RequestParam(required = false) String keyword,
        @RequestParam(required = false) String startTime,
        @RequestParam(required = false) String endTime) {
    return R.ok(service.page(pageNum, pageSize, ...));
}
```

Service 实现用 MyBatis-Plus LambdaQueryWrapper：

```java
public Page<Xxx> page(Integer pageNum, Integer pageSize, Long userId,
                     String status, String keyword, String startTime, String endTime) {
    LambdaQueryWrapper<Xxx> w = new LambdaQueryWrapper<>();
    w.eq(Xxx::getCreateBy, userId);
    if (status != null && !status.isEmpty()) w.eq(Xxx::getStatus, status);
    if (keyword != null && !keyword.isEmpty()) w.like(Xxx::getName, keyword.trim());
    if (startTime != null && !startTime.isEmpty()) w.ge(Xxx::getCreateTime, startTime);
    if (endTime != null && !endTime.isEmpty()) w.le(Xxx::getCreateTime, endTime);
    w.orderByDesc(Xxx::getCreateTime);
    return this.page(new Page<>(pageNum, pageSize), w);
}
```

> ⚠️ 前提：TenantMybatisPlusConfig 里已注册 PaginationInnerInterceptor，否则 this.page() 返回全量数据不分页。

## 8. Element Plus 树形表格展开/收起修复（菜单管理页，2026-10-26）

### 7.1 expand-row-keys 的已知坑

`expand-row-keys` 对深层嵌套的树形表格**不可靠**——Vue 数组引用不变时 el-table 的 treeStore 不重算，且只做顶层 key 匹配，不保证子级自动展开。

### 7.2 ✅ 正确做法：toggleRowExpansion 官方 API

```vue
<el-table
  ref="tableRef"
  :data="filteredData"
  row-key="id"
  :tree-props="{ children: 'children', hasChildren: 'hasChildren' }"
  border
>
  <!-- 列定义 -->
</el-table>

<script setup>
import { ref, nextTick } from 'vue'

const tableRef = ref(null)
const filteredData = ref([])  // 树形数据（buildTree 后的结构）

const expandAll = () => {
  const table = tableRef.value
  if (!table) return
  // 展开：从外到内（父先开让子级 DOM 出现）
  const walk = (list) => {
    for (const node of list) {
      if (node.children?.length) {
        table.toggleRowExpansion(node, true)
        walk(node.children)
      }
    }
  }
  nextTick(() => walk(filteredData.value))
}

const collapseAll = () => {
  const table = tableRef.value
  if (!table) return
  // 收起：从内到外（子先收，否则父收起后子级 DOM 没了 toggle 不到）
  const walk = (list) => {
    for (const node of list) {
      if (node.children?.length) {
        walk(node.children)
        table.toggleRowExpansion(node, false)
      }
    }
  }
  nextTick(() => walk(filteredData.value))
}

// fetchData 后默认全部展开（替代 :default-expand-all）
const fetchData = async () => {
  ...
  treeData.value = buildTree(flatList)
  nextTick(expandAll)
}
</script>
```

### 7.3 为什么展开和收起递归顺序不同

| 操作 | 顺序 | 原因 |
|---|---|---|
| 展开 | **从外到内** | 父级展开后子级 DOM 才出现，才能 toggleRowExpansion 子级 |
| 收起 | **从内到外** | 父级收起后子级 DOM 消失，toggleRowExpansion 子级就失效了 |

## 11. el-option value 类型必须与后端参数类型严格一致

### 10.1 现象
后端期望 `messageType` 是 Integer（1=通知, 2=公告），前端 el-option value 写字符串：

```vue
<!-- ❌ 错误：value 是字符串 -->
<el-option label="通知" value="1" />
<el-option label="公告" value="2" />

<!-- ✅ 正确：:value 绑定数字（注意冒号前缀） -->
<el-option label="通知" :value="1" />
<el-option label="公告" :value="2" />
```

后端 `@RequestParam Integer messageType` 接收到字符串 '1' 会尝试转换，部分场景（如空字符串、'1 ' 带空格）会抛 `NumberFormatException` 或静默失败查不到数据。

### 10.2 检查口诀

> **看后端 Controller 的 `@RequestParam` 类型，el-option value 就用什么类型绑定**。
> - `Integer` → `:value="1"`
> - `Long` → `:value="100"`
> - `String` → `value="all"`（不带冒号）

## 13. HTTP IP 端口下 navigator.clipboard 兼容方案

### 13.1 问题
`http://IP:端口` 非 HTTPS 环境下，浏览器安全策略禁用了 Clipboard API：
```js
navigator.clipboard  // undefined
```

### ✅ 标准 fallback（Clipboard API + execCommand 双重保险）

```js
const copyToClipboard = async (text) => {
  try {
    // 优先 Clipboard API（HTTPS 或 localhost 可用）
    if (navigator.clipboard && window.isSecureContext) {
      await navigator.clipboard.writeText(text)
      ElMessage.success('已复制')
      return
    }
  } catch (e) {
    // Clipboard API 不可用或用户拒绝
  }

  // fallback：document.execCommand('copy')（已被废弃但兼容性最强）
  const textarea = document.createElement('textarea')
  textarea.value = text
  textarea.style.position = 'fixed'
  textarea.style.opacity = '0'
  document.body.appendChild(textarea)
  textarea.select()
  try {
    document.execCommand('copy')
    ElMessage.success('已复制')
  } catch (e) {
    ElMessage.error('复制失败，请手动复制')
  }
  document.body.removeChild(textarea)
}
```

## 16. 全局 v-hasPermi 权限指令使用规范（2026-11-03 新增，全量落地完成）

> 权限码唯一事实源：`sys_menu` 表 `perms` 字段。前端指令、后端 `@RequiresPermission` 注解全部从此复制，零自定义拼写。
> 后端接口鉴权为最终安全底线，前端仅做显隐体验控制——禁止仅靠前端隐藏按钮做安全防护。
> 完整权限码清单 👉 参考：13 - 按钮级权限.md § 四

### 16.1 指令实现原理

```javascript
// src/directives/permission.js
// 全局注册：main.js → setupPermissionDirective(app)
// 判断逻辑：pinia user store 的 hasPerm getter（已原生支持 *:*:* 通配符）
// 隐藏方式：el.style.display = 'none'（不修改 DOM 结构，避免虚拟节点 diff 异常）

export const hasPermi = {
  mounted(el, binding) {
    const store = useUserStore()
    const permList = Array.isArray(binding.value) ? binding.value : [binding.value]
    const hasAny = permList.some(p => store.hasPerm(p))
    if (!hasAny) { el.style.display = 'none' }
  },
  // updated 钩子：角色切换 / 重新登录后自动刷新
  updated(el, binding) {
    const store = useUserStore()
    const permList = Array.isArray(binding.value) ? binding.value : [binding.value]
    const hasAny = permList.some(p => store.hasPerm(p))
    el.style.display = hasAny ? '' : 'none'
  }
}
```

### 16.3 绑定规则与约束

| # | 规则 | 说明 |
|---|---|---|
| 1 | **一个按钮绑一个权限码** | 单字符串数组 `['xxx:xxx:xxx']`，多权限仅特殊场景用 |
| 2 | **权限码严格对齐 sys_menu.perms** | 禁止自造拼写，大小写/冒号/符号必须完全一致 |
| 3 | **后端有 @RequiresPermission 注解 → 前端必须绑** | 写操作（新增/编辑/删除/发布/分发/重置密码）100% 绑定 |
| 4 | **前端独用按钮（preview/designer）也必须绑** | 无权限直接隐藏入口，不要让用户进了画布保存才报错 |
| 5 | **designer 按钮是最高优先级** | workflow:definition:designer / form:definition:designer → 无权限看不到按钮 |
| 6 | **preview 按钮也绑** | form:definition:preview / workflow:definition:preview → 同上理由 |
| 7 | **list/query 读权限一般不绑按钮** | 列表页查询按钮、详情页查看按钮通常不需要权限控制 |
| 8 | **超管 `*:*:*` 通配符前端已原生支持** | pinia store.hasPerm 会返回 true，超管看到所有按钮 |
| 9 | **不绑权限的按钮=所有人可见** | 删除前先 grep 确认后端有没有注解，有注解就必须绑 |

## 18. 双 Controller 镜像开发规范（平台侧 ↔ 租户侧对齐操作手册）

> 本项目采用**平台侧 Controller**（`/system/**`）+ **租户侧 Controller**（`/tenant/**`）双接口架构。
> 开发时必须时刻搞清楚：你改的是哪一侧？另一侧需不需要镜像同步？

### 18.1 架构认知

```
┌─────────────────────────────────────────────────────────┐
│                      前端 SPA（一套）                     │
│  src/views/system/user/index.vue  ← 平台侧和租户侧共用   │
│  用 isTenantLogin = computed(() => storage.getLoginType() === 'tenant')
│  来决定显示哪些列/按钮/表单项                             │
└────────────┬────────────────────────────┬───────────────┘
             │ API 调用前缀                │
             ▼                            ▼
┌───────────────────┐          ┌──────────────────────┐
│  平台侧 Controller │          │   租户侧 Controller   │
│  /system/user/**  │          │   /tenant/user/**    │
│  SysUserController│          │   TenantUserController│
└───────────────────┘          └──────────────────────┘
```

| 维度 | 平台侧 `/system/**` | 租户侧 `/tenant/**` |
|------|---------------------|---------------------|
| Controller | `SysUserController`、`SysTenantController` | `TenantUserController`、`TenantRoleController` 等 |
| 数据库过滤 | `CustomTenantHandler.skip()` 可跨租户查询 | SQL 自动加 `WHERE tenant_id = 当前用户tenantId`，无法越权 |
| 典型操作 | 管理所有租户、跨租户查用户、创建平台角色 | 管理本租户用户/角色/部门/菜单 |
| 前端入口 | 平台管理员登录后进入 | 租户管理员登录后进入 |

### 18.2 明确区分三类内容

#### ✅ 只在平台侧有（租户侧完全不存在）

| 模块 | 接口/功能 | 说明 |
|------|----------|------|
| 租户管理 | `/system/tenant/**` 全套接口 | 租户侧没有租户管理，自己就是租户 |
| 用户管理-详情入口 | 列表操作列的【详情】按钮（v-if="!isTenantLogin"） | 本次新增的详情弹窗，租户侧不显示入口 |
| 用户管理-跨租户详情 | `/system/user/{id}/detail` 接口内的 skip 逻辑 | 租户侧查不到别的租户用户，不需要这个逻辑 |
| 角色管理-平台角色 | tenantId=0 的角色 | 租户侧只能创建 tenantId=自身id 的角色 |
| 所有系统监控 | `/system/monitor/**` | 租户侧看不到全局监控 |

#### 🔄 共用组件但有条件差异（isTenantLogin 控制）

| 模块 | 文件 | 平台侧显示 | 租户侧显示 |
|------|------|-----------|-----------|
| 用户管理列表 | `views/system/user/index.vue` | 8 列 + 详情按钮 | 6 列（去掉所属租户列和详情按钮） |
| 角色管理弹窗 | `views/system/role/index.vue` | 所属租户下拉必选 | 所属租户 disabled 自动填当前租户 |

| API 调用前缀 | `api/user.js` 的 `getUrl()` 辅助函数 | 返回 `/system/user` | 返回 `/tenant/user` |

#### ❌ 只在租户侧有（平台侧不显示）

当前项目租户侧没有独有页面——**所有租户侧页面都是共用组件通过 isTenantLogin 裁剪而来**。如果以后有租户独占功能（比如租户级账单、租户级审批流），需要新建独立 view 目录并单独建路由。

### 18.3 镜像开发操作清单

**当你在平台侧加了一个功能时，问自己 4 个问题：**

| # | 问题 | 动作 |
|---|------|------|
| 1 | 租户侧是否**也需要**这个功能？ | 不需要 → 加 `v-if="!isTenantLogin"` 隐藏入口，后端接口 skip/reset 只在平台侧 Controller |
| 2 | 租户侧需要的功能**范围一样吗**？ | 范围不同 → 共用组件 + isTenantLogin 裁剪差异部分（如列表列、弹窗字段） |
| 3 | 后端是否需要**镜像接口**？ | 平台侧在 SysXxxController 加了 /system/xxx/detail → 租户侧可能需要在 TenantXxxController 加 /tenant/xxx/detail（如果租户管理员也要看详情） |
| 4 | 新增 API 函数**前缀写死了吗**？ | `api/xxx.js` 里写 `url: '/system/xxx/detail'` → 平台侧专用；用 `getUrl('/xxx/detail')` → 自动按登录类型选前缀 |

| # | 位置 | 操作 |
|---|------|------|
| 1 | **后端** `TenantUserController.java` | 新增 `GET /tenant/user/{id}/detail` 接口，**不需要** `CustomTenantHandler.skip()`（TenantLine 自动只查本租户），复用 `UserDetailVO` 但 buildUserDetailVO 里的跨租户逻辑去掉（租户侧看不到别的租户数据） |

| 3 | **前端** `views/system/user/index.vue` | 详情弹窗模板**不动**（组件共用），只改 `handleDetail` 方法：根据 `isTenantLogin` 选择调哪个 API |

### 18.5 API 前缀规范速查

```javascript
// api/user.js —— 正确示例

// ✅ 需要按登录类型自动切换的（list/add/update/delete）
export function getUserList(params) {
  const isTenant = storage.getLoginType() === 'tenant'
  return request({
    url: isTenant ? '/tenant/user/list' : '/system/user/list',
    method: 'get',
    params
  })
}

// ✅ 平台侧专用（本次新增的详情接口，租户侧没权限也没入口）
export function getUserDetail(id) {
  return request({
    url: '/system/user/' + id + '/detail',   // ⭐ 写死 /system 前缀
    method: 'get'
  })
}

// ❌ 错误：详情接口也用 getUrl 辅助函数导致租户侧误调
export function getUserDetail(id) {
  return request({
    url: getUrl('/user/' + id + '/detail'),  // 如果以后租户侧加了这个接口会自动切，但现在会调不存在的 /tenant/user/{id}/detail → 404
    method: 'get'
  })
}
```

**口诀**：
> - **共用 CRUD** → 用 getUrl() 或 storage 判断自动选前缀
> - **平台侧独用** → 写死 `/system/xxx/...`
> - **租户侧独用** → 写死 `/tenant/xxx/...`
> - **不确定** → 先想清楚租户侧需不需要，再决定前缀策略

## 17. 列表精简 + 详情弹窗完整模式（2026-11-06 新增，租户/用户两个案例）

> 本次迭代完成了**租户管理详情**和**用户管理详情**两个功能，形成了完整的实现范式。
> 核心原则：**列表接口只返回列表需要的字段（轻量），详情接口独立存在（聚合），VO 各自独立不混用**。
> 参考：平台侧 Controller（`SysTenantController` / `SysUserController`）、前端 `src/api/tenant.js` / `src/api/user.js`

### 17.1 两个案例总览

| 项目 | 租户管理详情 | 用户管理详情 |
|------|------------|------------|
| 后端接口 | `GET /system/tenant/{id}/detail` | `GET /system/user/{id}/detail` |
| 后端 VO | `TenantDetailVO` + `TenantModuleItemVO` | `UserDetailVO` + `UserRoleItemVO` |
| 数据源 | `sys_tenant` 主表 + `sys_tenant_module` 子表 + Redis 过期状态修正 | `sys_user` 主表 + `sys_role`（关联 tenantId/deptId 区分归属）+ Redis permVer |
| 前端弹窗区块 | ① 基础信息 ② 已开通模块 ③ 扩展字段预留 | ① 基础 ② 归属 ③ 权限（DataScope + 角色列表）④ 运维信息 ⑤ 扩展字段预留 |
| 跨租户查询 | 不需要（租户是隔离主体） | **需要**（平台管理员可查任意租户用户） |

### 17.2 后端 VO 解耦规范（核心原则）

```
❌ 错误：复用列表 VO，导致列表接口冗余或详情接口缺字段
✅ 正确：列表 VO 和详情 VO 各自独立，互不依赖
```

**为什么不能复用？**
| 维度 | 列表 VO（TenantListVO / UserListVO） | 详情 VO（TenantDetailVO / UserDetailVO） |
|------|----|----|
| 字段数 | 8-12 个（列表列需要的） | 20-30 个（详情区块需要的） |
| 关联查询 | 轻量（join 1-2 张表） | 重量（join 3-5 张表 + Redis + 枚举转换） |
| 性能要求 | 高（分页批量返回） | 低（单条查询） |
| 使用场景 | /list 接口 | /{id}/detail 接口 |

### 17.3 三类典型数据源陷阱（本次踩过的）

#### 陷阱 A：permVer 不在数据库，在 Redis

```
// ❌ 错误：以为是 sys_user.perm_ver 字段直接 select
// ✅ 正确：从 Redis key 读取
String permVer = null;
try {
    permVer = stringRedisTemplate.opsForValue().get("sys:user:perm:ver:" + userId);
} catch (Exception e) {
    // Redis 异常静默，不阻断详情接口返回
    log.warn("读取 permVer 失败, userId={}", userId, e);
}
vo.setPermVer(permVer);
```

**前端展示约定**：
- `permVer != null` → 显示具体数字
- `permVer == null` → 显示「未初始化」（该用户还没触发过权限变更 bump）

#### 陷阱 B：密码修改时间项目未存储

`SysUser` 实体**没有 pwdUpdateTime 字段**，全项目 grep 不到任何密码修改时间的存储逻辑。

**约定处理**：详情 VO 中 `pwdUpdateTime` 固定返回 null，前端硬编码显示「未记录」。后续如果加了字段，后端赋值即可，前端无需改动。

#### 陷阱 C：角色归属三类区分（租户角色 / 平台角色 / 部门私有）

`sys_role` 表没有单独的 role_type 字段，归属类型由 tenantId + deptId 联合判定：

| 条件 | 归属类型 | roleScope | 前端标签 |
|------|---------|-----------|----------|
| `deptId != null && deptId > 0` | 部门私有角色 | `DEPT` | 绿色 |
| `tenantId != null && tenantId > 0` | 租户角色 | `TENANT` | 橙色 + 显示所属租户列 |
| 其他（tenantId=0/null, deptId=null） | 平台角色 | `PLATFORM` | 默认 |

```java
// 后端判定逻辑（UserDetailVO 组装时）
String roleScope;
if (role.getDeptId() != null && role.getDeptId() > 0) {
    roleScope = "DEPT";
} else if (role.getTenantId() != null && role.getTenantId() > 0) {
    roleScope = "TENANT";
} else {
    roleScope = "PLATFORM";
}
```

### 17.4 跨租户查询：TenantLine skip/reset 必须成对

平台管理员查任意租户用户详情时，需要绕过租户行级隔离：

```java
// SysUserController.java
@GetMapping("/{id}/detail")
public R<UserDetailVO> detail(@PathVariable Long id) {
    CustomTenantHandler.skip();   // ⭐ 开启 skip
    try {
        SysUser user = userService.getById(id);
        if (user == null) {
            return R.fail("用户不存在");
        }
        UserDetailVO vo = buildUserDetailVO(user);
        return R.ok(vo);
    } finally {
        CustomTenantHandler.reset();  // ⭐ finally 里必须 reset
    }
}
```

| # | 约束 | 原因 |
|---|------|------|
| 1 | **skip/reset 必须成对** | 如果详情接口异常抛出来没 reset，后续所有查询都不会加 tenant_id 过滤，越权查到别的租户数据 |
| 2 | **必须在 finally 块 reset** | 不能放在 try 块末尾，异常时会跳过 |
| 3 | **PermissionGuard 已经做了 L1 租户归属校验** | skip 只是绕过 SQL 层的 tenant_id 条件，权限层的校验仍然有效 |

### 17.6 隐性约束清单

| # | 约束 | 原因 |
|---|------|------|
| 1 | **详情接口必须独立于列表接口** | 列表分页接口不能塞聚合查询，详情单条接口不能被列表复用 |
| 2 | **destroy-on-close 必须开启** | 每次点详情都清空上一次数据，Object.assign 重新赋值，不残留旧数据 |
| 3 | **操作列顺序和数量严格对齐需求** | 平台侧用户管理操作列固定：**详情、编辑、重置密码、删除** |
| 4 | **平台侧独有的按钮必须加 v-if="!isTenantLogin"** | 租户侧登录时详情按钮自动隐藏，不能让租户管理员调平台侧详情接口（PermissionGuard 会拦截，但入口也应该隐藏） |
| 5 | **Redis 字段 try-catch 包裹** | Redis 挂了不影响详情主接口返回，该字段静默显示「未初始化」 |
| 6 | **枚举值映射前端辅助函数集中定义** | `roleScopeText()` / `dataScopeText()` / `roleScopeTagType()` 三个函数放在详情弹窗同文件顶部，不要散落到多个文件 |
| 7 | **列表精简后不要偷偷加列** | 需求说 8 列就是 8 列，不要因为方便加个「创建时间」或「邮箱」进去 |
