## 二、隐性约束 & 踩过的坑（血泪经验，必看！）

### 🔴 坑 1：PermissionGuard 三层校验与 TenantLineInnerInterceptor 冲突

**表现**：admin(tenantId=0) 调跨租户查询，TenantLineInnerInterceptor 自动追加 `WHERE tenant_id=0`，导致只能查到自己租户的数据。

**正确姿势**：
```java
customTenantHandler.skip(); try { // 这里面的所有 SQL 都不受租户拦截影响 allUsers = sysUserService.list(); } finally { customTenantHandler.reset(); }

text



- sendToAll / sendToUsers / sendToRoles 的 **save(message) 也要进 skip()**——不然 TenantLineInnerInterceptor 会自动把 tenant_id=0 塞进去
- 广播消息必须显式 `message.setTenantId(null)`，消息可见性由 sys_message_user 表（IGNORED_TABLES）精确控制

### 🔴 坑 2：Redis 手动 SET 假权限缓存会覆盖真实权限

**表现**：`redis-cli SET rbac:perms:7 '["fake:perm:test6"]'` 后，PermissionGuard 永远看到 fake 权限，你给用户分配的真实权限全部无效！

**原因**：
- rbac:perms 缓存无 TTL（或 TTL 很长），手动 SET 永久生效
- LoginUser.permissions 在登录时从 Redis 加载到 JWT/Token 里，后续请求直接从 LoginUser 读，不会再查 DB
- 清 Redis 不够，**必须重新登录**才能让 LoginUser 重建

**正确姿势（清理脏缓存）**：
```bash
redis-cli KEYS "rbac:" | xargs redis-cli DEL # 清权限缓存 redis-cli KEYS "login:" | xargs redis-cli DEL # 清登录态 redis-cli KEYS "token" | xargs redis-cli DEL # 清 token

然后重新登录拿新 token
text




### 🟡 坑 3：@RequiresPermission + PermissionGuard.check() 会被 PermissionAspect 重复执行

**表现**：Controller 方法既写了 `@RequiresPermission("xxx")` 又写了 `permissionGuard.check(scope, "xxx")`，PermissionAspect 切面先截一次，方法里又手动调一次。

**正确姿势（已经按这个做了）**：
- **AOP 层**：`@RequiresPermission` 由 PermissionAspect 拦截 → 自动调 `permissionGuard.check(null, ann.logical(), ann.value())`（targetScope=null，读操作模式）
- **Controller 手动调用**：用于写操作需要传 ResourceScope 的场景，**不要再加 @RequiresPermission**（避免重复）
- **只读接口**：list/getById 既不加 @RequiresPermission 也不手动调 check，让 PermissionGuard 完全跳过 L3，数据范围由 MP DataPermissionInterceptor SQL 兜底

### 🟡 坑 4：TenantUserController 接口路径

不是 `PUT /tenant/user/role-perm`，而是：
POST /tenant/user/saveRolePerm/{userId} Body: [roleId1, roleId2, ...] (纯 Long 数组，不是对象)

text




### 🟡 坑 5：废弃 Controller 拦截方式

不是抛异常，而是直接返回业务拦截消息：
```java
@GetMapping("/list") public R<?> list() { return R.fail("该接口暂未完成权限改造，禁止调用"); }

text




### 🟡 坑 6：test6 真实权限比预期多

之前以为 test6 没有 system:role:add / system:form:add，实际 DB + Redis 里都有。**不要猜用户权限，直接查**：
```bash
# 生产标准格式：rbac:perms:{tenantId}:{userId}
# 冒烟测试临时简写（仅手动验证用）：rbac:perms:{userId} 或 rbac:perms:7（test6 的 userId=7）
redis-cli GET "rbac:perms:{tenantId}:{userId}"  # 生产标准
# redis-cli GET "rbac:perms:7"  # 冒烟测试简写（手动查 test6 权限用）
```

### 🟡 坑 7：BusinessException handler 必须确保 AccessDeniedException 不走裸 HTTP 状态码

**GlobalExceptionHandler 约束**：
- PermissionGuard L1/L2 抛 `BusinessException(code=403, msg=...)` → GlobalExceptionHandler.handleBusinessException → 返回 `R.fail(403, msg)` ✅
- PermissionGuard L3 抛 `AccessDeniedException(msg)` → GlobalExceptionHandler.handleAccessDenied → 返回 `R.fail(403, msg)`，**不能加 @ResponseStatus(FORBIDDEN)** ✅
- 真实未知异常 → `handleException` → 返回 `R.fail(SERVER_ERROR, "系统繁忙，请稍后再试")` + `log.error(..., e)` 完整堆栈 ✅
