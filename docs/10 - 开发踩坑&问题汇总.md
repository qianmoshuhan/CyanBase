## 01 - 消息铃铛 SSE 改造（2026-10-29）

将消息铃铛从 30s HTTP 轮询改为 SSE Server-Sent Events 推送，涉及 Spring Boot SseEmitter + 原生 EventSource + nginx 长连接配置。

### 踩坑汇总

| # | 模块 | 坑 | 根因 | 教训 |
|---|------|----|------|------|
| 1 | 后端 Lombok | `variable xxx might not have been initialized` 编译报错 | 同时用了 `@RequiredArgsConstructor`（Lombok 自动生成带参构造器）和手写无参构造器，Java 编译器看到两条 final 字段初始化路径 → 安全检查失败 | **`@RequiredArgsConstructor` 和手写构造器二者只能取其一**；初始化逻辑（心跳调度、线程池启动）放 `@PostConstruct`，它在构造器注入全部完成后执行 |
| 2 | 后端 Spring 循环依赖 | `SysMessageServiceImpl ↔ SseEmitterManager` 循环 → 启动炸 | SSE Manager 注入 `SysMessageService` 接口，接口实现是 `SysMessageServiceImpl`，ServiceImpl 又注入 Manager → 形成环 | **Manager/基础设施类绝对不能注入 Service**，改用最底层 Mapper 直接查 DB；Mapper 无 Service 依赖，循环立断 |
| 3 | nginx location 匹配 | `/system/message/sse` 被正则 location 抢走，事件被攒一批才发 | 现有配置里 `location ~ ^/system/(...|message|...)/(.*)$` 这条正则匹配了 `/system/message/sse`，但正则 location 没关 `proxy_buffering` → SSE 事件被 nginx buffer 攒到 4KB 满才发 | **SSE 长连接必须用 `^~` 前缀匹配**：`location ^~ /system/message/sse` 写在所有正则 location 之前；`^~` 让 nginx 不再往下查正则 |
| 4 | nginx 长连接配置 | 即使 location 命中，SSE 仍 60s 断连或事件攒批 | nginx 默认 `proxy_http_version 1.0` 会自动加 `Connection: close`；默认 `proxy_buffering on` 会缓存事件 | **SSE 三剑客缺一不可**：① `proxy_http_version 1.1` ② `proxy_set_header Connection ''` 清掉 Hop-by-Hop ③ `proxy_buffering off` 关缓存；`proxy_read_timeout 3600s` 给足配合心跳 |
| 5 | EventSource 鉴权 | 原生 EventSource 不支持自定义 header，没法带 JWT | axios 能加 `Authorization: Bearer xxx`，但 EventSource API 只接受一个 URL 字符串 | **JwtAuthenticationFilter 必须加 query parameter fallback**：`request.getParameter("token")`；前端用 `EventSource('/system/message/sse?token=' + encodeURIComponent(token))` |
| 6 | Lombok final 字段重复声明 | `private final SseEmitterManager sseEmitterManager;` 写了两行 → 构造器参数重复 | diff 合并时手动补 import 和字段，不小心复制粘贴了两次 | **每个新字段声明后立即编译检查**；Accept 多个 diff 后必须 `mvn clean compile` 验证 |
| 7 | 前端事件监听混淆 | EventSource 的 `onmessage` / `addEventListener('xxx')` / `onerror` 三套 API 容易混乱 | EventSource 有两层事件：①浏览器内置的 `onerror`（连接层错误）②后端通过 `.name("xxx")` 指定的业务事件，用 `addEventListener('xxx')` 监听 | **明确分工**：业务计数变更 → `addEventListener('count', cb)`；后端主动通知 token 过期 → `addEventListener('error', cb)`；连接层断开/网络问题 → `onerror(cb)`，三者互不冲突 |

## 11 - 租户侧登录 + 用户管理手机号唯一性改造（2026-10-30）

今日完整改造链路：①租户侧登录从"租户下拉 + 用户名"改为"手机号 + 多租户弹窗"；②手机号移到用户管理表单顶部 + 必填 + 正则；③手机号租户内唯一性校验（后端兜底 + 前端实时校验）；④平台侧用户管理新增按租户筛选。

### 踩坑汇总

| # | 模块 | 坑 | 根因 | 教训 | 性质 |
|---|------|----|------|------|------|
| 1 | 后端 CustomTenantHandler | 误以为平台侧跨租户查询需要 `CustomTenantHandler.skip()` | 没读源码就加了 skip，导致 SysUserController.list() 里多了一层 skip 破坏 try-finally 结构 → 编译 21 条错误连锁 | **改代码前先读源码！** CustomTenantHandler.ignoreTable() 第 211-213 行：`tenantId == 0L` 直接 return true，所有表自动跳过拦截。平台 admin 登录（tenantId=0）的所有查询天然跨租户，不需要 skip | [P0] 必记 |
| 2 | 后端 try-finally 结构 | 错误 diff 先 Accept，修正版没 Accept，导致 SysUserController.list() 里 `try {` 没有配对的 `finally { reset(); }` → 21 条编译错误 | diff Accept 时序管理失控；try-finally 是块级结构，缺右括号整段悬空 | **每改一段完整块（try-finally / if-else / 方法）必须一次性展示、一次性 Accept**，不要拆成两个 diff 先 Accept 一半 | [P0] 必记 |
| 3 | 后端 CustomTenantHandler 嵌套 skip/reset | SysUserController.list() 外层加了 skip，内部 fillDeptName / fillPostName 也各自 skip-reset → 内层 reset 把外层也清了 | CustomTenantHandler 用 ThreadLocal `volatile boolean skipFlag` 单变量存储，不是计数器。多层 skip 幂等，但内层 reset 会直接置 false，不管外层还有没有未完成的 SQL | **skip/reset 必须最小化范围**：只包裹必须绕开拦截的那几行 SQL，不要包裹整个方法，尤其不要嵌套 | [P1] 架构约束 |
| 4 | 后端 MyBatis-Plus del_flag | TenantAuthServiceImpl 手写了 `.eq(SysUser::getDelFlag, 0)` → SQL 变成 `WHERE del_flag=0 AND del_flag=0` | SysUser.delFlag 字段有 `@TableLogic` 注解，MP 自动在所有 SELECT 里追加 `WHERE del_flag = 0`，手动再写一遍纯属冗余 | **@TableLogic 字段不要再手动写 eq 条件**；可以 grep 字段定义确认有没有 @TableLogic | [P1] MP 特性 |
| 5 | 后端 TenantLine 匿名访问 | 租户登录 loginWithoutTenant() 是匿名接口（不携带 JWT）→ SecurityUtils.getTenantId() = null → CustomTenantHandler.resolveTenantId() 返回 null → skip 判断为 true → SQL 自动跳过 tenant_id 追加 | 这是正常预期行为。但容易混淆：为什么匿名接口 TenantLine 不拦截？因为 resolveTenantId() 返回 null 时 skip | **写匿名接口里的跨租户查询（如登录手机号匹配），不需要 skip，TenantLine 天然放行** | [P1] 架构认知 |
| 6 | 前端 Element Plus 图标 | prefix-icon="I-phone" 图标不显示，浏览器控制台无报错 | Element Plus 图标库没有 "I-phone"。正确的手机号图标名是 "Cellphone"，可以在项目已用图标里 grep 确认 | **Element Plus 图标名不带前缀**，直接写 PascalCase：Cellphone / Lock / User；写之前 grep 项目已有代码里用了哪些图标 | [P2] 低级拼写 |
| 7 | 前端 async validator | formRules 里 phone 用自定义 async validator 做实时唯一性校验 | Element Plus 支持 `validator: async (rule, value, callback)` 写法，校验通过显式 `callback()`，失败 `callback(new Error('xxx'))`；不要写 return Promise | **async validator 模板**：①必填规则和正则规则先拦截；②业务逻辑里 try-catch，catch 里不要阻塞提交（后端 Controller 还有兜底校验） | [P1] 前端规范 |
| 8 | 后端接口废弃 | `/tenant-auth/tenant/list` 旧租户下拉接口没有在前端删除，后端也没清理 | 改造过程中**先改前端**（下拉组件删掉 → 前端不再调用），再删后端接口。本次已删除。注意：改完后要 grep 全项目有没有其他地方还在调这个接口 | **删除接口前先 grep 确认无引用**，不要盲删 | [P1] 接口管理 |
| 9 | 后端 VO 清理 | TenantItemVO.java 是旧租户下拉列表 VO，改造后 TenantAuthController 和 TenantUserController 都不再 import | 遗留旧文件不影响编译，但属于技术债。本次改造后该 VO 可删 | **改完一个功能后 grep 旧类/旧文件有没有被引用**，没引用的清理掉 | [P2] 技术债清理 |
| 10 | 后端 SysUser.phone 唯一性 | checkPhone 接口返回 R<Boolean>，前端判断 res.data → 为 true 才通过 | 后端 `return R.ok(sysUserService.count(wrapper) == 0)` → R.data 是 Boolean；前端 request 拦截器已拆一层 axios → res 就是 R 结构 → res.data 是 Boolean | **R.ok(Boolean) → 前端 res.data 直接是 Boolean**，不要再 .data.data | [P1] R 结构取值 |
| 11 | 后端平台侧跨租户查手机号 | SysUserController.update() 的手机号校验需要 skip TenantLine | 平台管理员（tenantId=0）要给 tenantId=5 的租户新增用户，skip TenantLine 后手动查 `WHERE tenant_id=5 AND phone=xxx` 才能跨租户查到 | **虽然 admin 自动 skip 了，但手动构造 LambdaQueryWrapper 加 tenantId 精确过滤时，skip 包一层也无害**（防御性编程：万一未来 CustomTenantHandler 逻辑改了） | [P2] 防御性编程 |
| 12 | DB sys_user phone 字段允许 NULL | 表里有一些用户 phone 为空（如 id=4 test 用户） | 这些用户改造后登录不了，需要运维补全手机号 | **需求里说"当前所有有效用户都已补全唯一手机号"，改造前要先 SHOW FULL COLUMNS + SELECT COUNT(*) WHERE phone IS NULL 确认** | [P2] 数据质量 |
| 13 | 前端 el-option value 类型 | 租户筛选下拉 `:value="0"`（平台用户）必须是 Number | 和之前坑点 #25 一样：后端 `@RequestParam Long tenantId` 接 String "0" 会 NumberFormatException | **el-option 给后端传 Long/Integer 参数一律用 `:value` 绑定数字** | [P1] 类型对齐 |
| 14 | 多租户账号密码不一致弹窗行为 | 用户手机号 13000000001 在租户 A 密码 "111111"、在租户 B 密码 "222222"，用户输入密码 "111111" → 直接进租户 A，不弹窗 | 代码逻辑：用户输入密码后遍历所有候选账号验证密码，匹配到几个就是几个。只有匹配到 ≥2 个才弹窗。两个租户密码不一样 → 只匹配到一个 → 直接进 | **登录链路是"密码匹配精准命中"而非"先选租户再验密码"**；弹窗只在"同一个密码同时对多个租户账号有效"时触发 | [P1] 业务逻辑 |
| 15 | CustomTenantHandler 三层判断：tenantId==0 vs tenantId==null vs tenantId>0 | tenantId==0 → ignoreTable() return true（跳过拦截）；tenantId==null（匿名接口）→ resolveTenantId() return null → skip；tenantId>0 → 正常拦截追加 WHERE tenant_id=? | 三种情况要区分开，匿名接口和 admin 都不会被拦截，但原因完全不同 | **匿名接口：skip=true；admin：ignoreTable=true；普通租户：正常拦截** | [P0] 必记 |
