# 权限码维护铁律 + 隐性约束 + 注意事项（可直接放进 RBAC 文档末尾，作为运维开发手册）

>
> 适用：新增、修改、删除权限码，新增按钮接口，整改存量权限；底座非三重一大模块，sydyd 模块暂不适用这套约束。

## 一、核心铁律（强制，违反就会出 BUG / 安全漏洞）

1. **三位一体同源原则**
   新增任何操作按钮 / 接口，必须同时完成三件事，缺一不可：
   ① `sys_menu`插入 / 更新记录（menu_type=2 页面 / 3 按钮）；
   ② Controller 接口增加`@RequiresPermission("xxx:xxx:xxx")`注解；
   ③ 前端按钮绑定`v‑hasPermi="['xxx:xxx:xxx']"`；
   ④ 更新权限盘点文档`docs/permission‑checklist.md`。

>
> 禁止出现：只有前端权限码、数据库有记录后端无注解、后端有注解数据库无记录。

2. **权限码是字符串事实源，sys_menu 表为唯一事实来源**

- 后端注解、前端指令，全部复制 sys_menu 里面的`perms`字符串，手敲容易打错；
- 修改权限码命名，**必须 UPDATE sys_menu.perms，再同步改后端、前端、文档，不能只改一端**。

3. **前端只做体验，鉴权永远信任后端**

- v‑hasPermi 只是控制按钮显隐；
- 绕过前端直接调用 HTTP 接口，后端`@RequiresPermission`必须依然能拦截无权限请求；
- 绝不允许 “仅靠前端隐藏按钮做安全防护”（例如 preview、designer 入口接口）。

4. **命名强制范式 `模块:资源:动作`**

>
> 示例：`workflow:definition:save`、`form:definition:preview`

- 模块：`system / workflow:definition / form:definition / monitor`；
- 资源：`user、role、definition、tenant`；
- 动作动词规范：
    - 列表查询：`list`
    - 单条详情查询：`query`（**管理类才拆分；能看 list 一般可复用 list，不盲目新增 query**）
    - 新增：`add`；修改：`edit`；**仅流程 / 表单定义收敛为`save`，其它模块严禁照搬 save**
    - 单条删除：`delete`（废弃`remove`）
    - 批量清空：`clean`
    - 特殊业务动作：`preview、designer、publish、distribute、transfer、approve`。

5. **区分三类权限，不要混为一谈**
   1）**页面菜单权限 menu_type=2**：控制侧边栏路由入口是否显示；只控制 “能不能进页面”，不控制页面内部按钮接口；
   2）**按钮 L3 权限 menu_type=3**：`@RequiresPermission`做接口鉴权，控制接口调用；
   3）**行级数据过滤**：个人工作台（我的待办、我的已办），不新增 list 按钮权限，靠接口内部`where userId = 当前登录人`过滤数据。
6. **不要为了接口存在，硬造没有业务按钮的权限码**

>
> 典型反面案例：`monitor:api:add`，业务没有人工新增按钮，接口是系统自动采集，就不该加注解，不要为了 “每个接口都有注解” 强行造权限。

7. **高危写操作必须独立权限码**
   删除、分发、发布、分配租户、重置密码这类高危动作，必须独立权限，禁止复用 list、edit 权限。
8. **超管通配符 `*:*:*` 只在代码 PermissionGuard 硬编码放行，**sys_menu 绝不插入该记录 **。

## 二、隐性约束（踩过坑总结，容易忽略）

1. **sys_role_menu 存的是 menu_id，不是 perms 字符串**

- UPDATE sys_menu.perms 修改权限码名字：**已经分配给角色的按钮不受影响，自动跟随新 perms 生效**；
- INSERT 新增 menu_type=3 按钮记录：老角色**不会自动勾选新按钮**，必须平台管理员手动去角色管理勾选分配。

2. **租户侧 Controller 可以复用平台侧同一套权限码，不需要再新建一套 xxx:tenant:* 权限码**

>
> 现状：TenantUserController 复用`system:user:*`，靠 L1 租户隔离区分数据范围，不要重复造权限码。

3. **粒度取舍原则：不要过度拆分，也不要过度合并**

- ✅ 管理后台：列表`list`一般包含查看单条详情，不强行拆分`query`；只有特殊强安全管控才拆 list 与 query；
- ✅ 个人工作台数据（我的待办 / 我的已办）：页面菜单控制入口，接口行过滤，**不新增独立 list 按钮权限**；
- ✅ 能打开画布 designer ≠ 可以 save 保存；preview 预览 ≠ designer 设计；publish 发布 ≠ distribute 跨租户分发，语义必须拆开，不能复用。

4. **存量可以复用同一个权限码给多个接口，但新增接口尽量语义匹配**

>
> 现状：`workflow:definition:save`被十多处接口复用属于存量技术债，本次不重构；**新写接口禁止随意复用已有权限码，优先新建语义匹配权限码**。
> 注意警惕语义错配：例如把抄送列表查询复用`workflow:approve`，属于技术债，文档标记，后续迭代再修复。

5. **menu_type=2 页面菜单 ≠ 接口鉴权**
   页面菜单只是路由显隐；页面里面所有写接口、特殊读接口依然需要 L3 按钮权限注解；页面菜单存在，不等于接口可以裸跑。
6. **预埋按钮记录处理规则**
   数据库 sys_menu 可以提前预埋 menu_type=3 按钮记录（后端接口尚未开发完成），但是：

>
> 接口没有实现前，**不要加 @RequiresPermission 注解**；接口真正落地开发完成，再补上注解；文档标记 “后端待实现”。

## 三、禁止行为黑名单（绝对不要做）

❌ 禁止：只有前端写 v‑hasPermi，数据库、后端都没有对应记录 / 注解；
❌ 禁止：修改权限码只改后端、不改 sys_menu 数据库；
❌ 禁止：把个人工作台私有数据查询强行加上 list 按钮权限，极易出现 “菜单可见但是列表刷不出数据” 运维故障；
❌ 禁止：混淆`publish`版本发布 和 `distribute`跨租户分发；
❌ 禁止：全模块无脑把 add+edit 统一收敛为 save，**save 收敛仅限 form:definition /workflow:definition 两个模块**；
❌ 禁止继续使用`:remove`做单条删除动作，统一使用`:delete`，批量清空使用`:clean`；
❌ 禁止为系统内部自动调用的后台接口硬加 @RequiresPermission，无业务按钮就不要权限码；
❌ 禁止 sys_menu 插入`*:*:*`记录，超管放行只放在代码层。

## 四、权限变更之后必做自测清单（新增 / 修改权限码后执行）

1. 绕过前端直接 HTTP 调用接口，无权限账号访问，后端返回权限不足；
2. 拥有权限账号，接口访问正常；
3. 角色管理页面，可以正常勾选该新增按钮；
4. 前端按钮 v‑hasPermi：有权显示，无权限隐藏；
5. 如果是 INSERT 新增按钮：确认老角色默认不勾选，需要管理员手动分配；
6. 文档`permission‑checklist.md`同步更新。

## 五、存量问题处理策略

1. 存量重复权限码、语义不匹配：**不大规模重构**，只在文档标记为技术债；只有对应模块迭代改造的时候顺便修复；
2. B 类预埋按钮记录（后端待实现）：不动库表，文档标记，接口落地才补注解；
3. A 类已经实现业务接口但是缺少注解：**必须补上，属于安全漏洞，不能拖延**。

## 六、快速排查问题思路（线上出权限问题）

1. 查 sys_menu 表，确认 perms 字符串和后端注解完全一模一样，没有大小写、符号错误；
2. 确认角色对应的 role‑menu 关联表`sys_role_menu`，该按钮的 menu_id 已经分配给角色；
3. 确认登录用户返回的`permissionCodes`集合里面包含该权限码；
4. 绕过前端直接调用接口，确认后端 @RequiresPermission 拦截是否生效；
5. 区分：是前端按钮不显示，还是后端接口直接报错无权限，定位问题在哪一层。
